# Лабораторная работа 3 Проектирование платформы онлайн курсов по математике

## Предметная область

Платформа помогает школьникам и студентам выбирать онлайн курсы по математике, оплачивать доступ и получать учебные материалы. Преподаватель публикует курс с фиксированной ценой, а студент записывается на него. После успешной оплаты запись становится активной и студент получает письмо. При отказе платежа запись отменяется; при сбое открытия доступа выполняется возврат. Эта лабораторная содержит проектные спецификации для следующих работ; действующий сайт лабораторных 1–2 пока не реализует описанные сервисы.

Акторы: студент, преподаватель, администратор, внешний платёжный шлюз, почтовый провайдер.

Пользовательские сценарии:

1. Как студент, я хочу просмотреть каталог курсов, чтобы выбрать нужную тему.
2. Как студент, я хочу открыть описание курса, чтобы увидеть программу и стоимость.
3. Как студент, я хочу записаться на курс, чтобы получить доступ к урокам.
4. Как студент, я хочу увидеть состояние записи, чтобы узнать результат оплаты.
5. Как студент, я хочу просмотреть свои записи на курсы, чтобы продолжить обучение.
6. Как преподаватель, я хочу опубликовать курс, чтобы студенты могли записаться.
7. Как студент, я хочу получить письмо об успешной записи или отказе, чтобы не отслеживать состояние вручную.

## События и ограниченные контексты

Доменные события: `course.updated`, `enrollment.created`, `payment.succeeded`, `payment.failed`, `enrollment.activated`, `enrollment.cancelled`, `payment.refunded`.

| Контекст | Глоссарий |
|---|---|
| Каталог | Курс — программа по теме математики; преподаватель — автор курса; цена — стоимость доступа на момент публикации; публикация — разрешение записи студентов |
| Запись и доступ | Запись — связь студента с курсом; ожидание оплаты — доступ ещё закрыт; активация — открытие уроков; отмена — прекращение сценария покупки |
| Платежи | Платёж — попытка списания; шлюз — внешний обработчик оплаты; возврат — компенсация успешного списания; сумма — зафиксированная стоимость записи |
| Уведомления | Уведомление — сообщение студенту; шаблон — текст для события; доставка — результат отправки; повтор — попытка после временного отказа провайдера |

## Бизнес сервисы

### catalog-service

Отвечает за публикацию и чтение курсов, программу и стоимость. Единственный владелец `Course`. Предоставляет `POST /api/v1/courses` для преподавателя, `GET /api/v1/courses`, `GET /api/v1/courses/{courseId}` и внутреннюю проверку курса; публикует `course.updated`. Не зависит от других бизнес сервисов. Ожидаемая нагрузка: до 500 чтений в секунду, p95 до 150 мс. Каталог отделён от записи, поскольку читается значительно чаще и обновляется преподавателями независимо от покупок.

### enrollment-service

Отвечает за запись студента, состояние доступа и сагу покупки. Единственный владелец `Enrollment`; хранит зафиксированную цену, полученную от каталога при создании записи. Предоставляет создание и чтение записей, внутренние операции активации и отмены; публикует `enrollment.created`, `enrollment.activated`, `enrollment.cancelled`. Синхронно проверяет курс в catalog, при восстановлении после сбоя сверяет оплату в payment; подписан на `payment.succeeded`, `payment.failed`, `payment.refunded`, `course.updated`. До 30 созданий в минуту, p95 создания до 500 мс без ожидания платёжного шлюза. Отдельный сервис нужен из-за собственного жизненного цикла доступа и необходимости атомарно менять его состояние.

### payment-service

Отвечает за списания и возвраты через внешний шлюз. Единственный владелец `Payment` и журнала операций шлюза. Предоставляет чтение платежа, внутренние списание и возврат; публикует `payment.succeeded`, `payment.failed`, `payment.refunded`. Подписан на `enrollment.created`; при сверке вызывает внутренний API enrollment. До 30 операций в минуту, таймаут шлюза 5 с, все результаты аудируются. Сервис выделен из-за внешних секретов, идемпотентности и требований к аудиту.

### notification-service

Отвечает за письма и историю доставки. Единственный владелец `Notification` и попыток отправки. Предоставляет чтение уведомлений, подписан на `enrollment.activated`, `enrollment.cancelled`, `payment.refunded`. До 100 писем в минуту, допустимая задержка доставки 1 минута. Отказ почты не должен отменять оплаченную запись.

Отвергнуто объединение каталога и записи: у них разные владельцы изменений и несопоставимая нагрузка. Отвергнуто объединение записи и оплаты: платёжный шлюз требует изолировать секреты и аудит; его отказ не должен блокировать чтение учебных записей.

| Внешний платёжный шлюз | payment | Списание и возврат без хранения данных банковских карт |
| Почтовый провайдер | notification | Отправка писем с повтором при временном отказе |

## Схемы и взаимодействия

[Редактируемая архитектурная схема](docs/architecture.drawio) · [PNG архитектуры](docs/architecture.png) · [успешная покупка](docs/sequence-success.png) · [отказ оплаты](docs/sequence-failure.png).

Клиент вызывает сервисы только через Gateway. Все четыре сервиса и их отдельные БД размещены во внутренней сети; внешний порт есть только у Gateway. JWT проверяется на входе, `studentId` берётся из проверенного токена. Сервисы общаются по внутреннему DNS и сервисным токенам.

| № | Инициатор → получатель | Тип | Контракт |
|---|---|---|---|
| 1 | клиент → Gateway → catalog | REST | `GET /api/v1/courses`, `GET /api/v1/courses/{courseId}` |
| 2 | клиент → Gateway → enrollment | REST | `POST /api/v1/enrollments`, `GET /api/v1/enrollments` |
| 3 | клиент → Gateway → payment | REST | `GET /api/v1/payments/{paymentId}` |
| 4 | enrollment → catalog | REST | `GET /internal/v1/courses/{courseId}` для проверки публикации и цены, таймаут 300 мс |
| 5 | enrollment → payment | REST | `GET /internal/v1/payments/{paymentId}` для сверки после сбоя, таймаут 500 мс |
| 6 | payment → enrollment | REST | `GET /internal/v1/enrollments/{enrollmentId}` для сверки при пропуске события, таймаут 500 мс |
| 7 | enrollment → RabbitMQ → payment | событие | `enrollment.created` |
| 8 | payment → RabbitMQ → enrollment | событие | `payment.succeeded`, `payment.failed` |
| 9 | enrollment → RabbitMQ → notification | событие | `enrollment.activated`, `enrollment.cancelled` |
| 10 | payment → RabbitMQ → notification | событие | `payment.refunded` |
| 11 | catalog → RabbitMQ → enrollment | событие | `course.updated` |

Три синхронных межсервисных вызова — строки 4–6. Сверки выполняются в фоне после сбоя; обычная покупка не ждёт их. Брокер использует exchange `mathcourses.events`, routing key равен имени события. Каждое сообщение содержит `eventId`, `eventType`, `occurredAt`, `schemaVersion`, `correlationId`, `payload`. Схемы событий записаны в `components/schemas` OpenAPI издателя и подписчиков.

## Сага покупки курса

Студент создаёт запись с `Idempotency-Key`. Enrollment проверяет публикацию и цену курса, фиксирует цену и состояние `PENDING_PAYMENT`, затем в одной локальной транзакции сохраняет запись и outbox событие `enrollment.created`. API сразу возвращает `201`. Payment списывает сумму и публикует `payment.succeeded`. Enrollment открывает доступ, переводит запись в `ACTIVE`, публикует `enrollment.activated`. Notification отправляет письмо.

Если курс снят с публикации до создания записи, возвращается `409`, платёж не создаётся. Если платёж отклонён, событие `payment.failed` переводит запись в `CANCELLED`; уведомление отправляется отдельно. Если деньги списаны, но открытие доступа после повторов не удалось, enrollment переводит запись в `REFUND_PENDING` и отправляет идемпотентную команду возврата payment; после `payment.refunded` запись становится `CANCELLED`. Пока шлюз возврата недоступен, команда повторяется через DLQ, затем требует ручной проверки. Если не доставлено письмо, покупка не откатывается. Повторы событий поглощаются inbox таблицей по `eventId`, а повторные запросы к шлюзу используют тот же ключ идемпотентности. `correlationId` связывает шаги одной покупки. Периодическая сверка устраняет расхождения после длительной недоступности брокера.

## Лабораторная работа 4 Реализация микросервисов

Проектная модель выше реализована в `services/`. Используется Node.js 22 и Express 5: один язык и единый способ обработки ошибок упрощают поддержку четырёх сервисов. У каждого сервиса есть собственное JSON-хранилище в отдельном Docker volume. Такой файловый in-memory-подобный вариант разрешён заданием и позволяет запускать лабораторную без четырёх СУБД, при этом сервисы не читают данные друг друга.

| Сервис | Реализация | Хранилище | Взаимодействия |
|---|---|---|---|
| `catalog-service` | Публикация и чтение курсов | `catalog_data` | REST для `enrollment`, событие `course.updated` |
| `enrollment-service` | Запись студента и сага покупки | `enrollment_data` | REST к catalog/payment, события RabbitMQ |
| `payment-service` | Списание и возврат | `payment_data` | Обрабатывает `enrollment.created`, публикует `payment.*` |
| `notification-service` | Журнал уведомлений | `notification_data` | Обрабатывает `enrollment.*` и `payment.refunded` |

RabbitMQ является реальным брокером. Платёжный шлюз замокан в `payment-service`: `PAYMENT_MODE=success` публикует `payment.succeeded`, `PAYMENT_MODE=fail` — `payment.failed`. Почтовый провайдер замокан в `notification-service`: сервис сохраняет факт отправки с `deliveredBy: "email mock"`. Эти два мока не меняют форматы API и событий.

Keycloak на этапе лабораторной №4 не запускается: Gateway реализован минимально и служит единственной точкой маршрутизации. Проверка JWT считается замоканной инфраструктурной функцией; это допустимо по заданию для Gateway и внешних компонентов.

### Запуск

```bash
cd lab3
cp .env.example .env
docker compose up --build
```

Внешний доступ есть только у Gateway: `http://localhost:8081`. Внутренние сервисы и RabbitMQ не публикуют портов на хост. Проверка:

```bash
curl http://localhost:8081/health
curl http://localhost:8081/api/v1/courses
curl -X POST http://localhost:8081/api/v1/enrollments \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-1' \
  -d '{"courseId":"course-101"}'
```

Через несколько секунд получите состояние записи по `GET /api/v1/enrollments/{id}`. В режиме `success` оно станет `ACTIVE`; в режиме `fail` — `CANCELLED`. Команды и ожидаемые результаты приведены в [сценариях демонстрации](docs/demo-scenarios.md).

Три фактических синхронных вызова: `enrollment → catalog` при создании записи, `enrollment → payment` при сверке и `payment → enrollment` при сверке. Асинхронная часть реализована через RabbitMQ: `enrollment.created → payment`, `payment.succeeded/payment.failed → enrollment`, `enrollment.activated/enrollment.cancelled → notification`.

Каждый POST, который создаёт или меняет бизнес-состояние, требует `Idempotency-Key`. Ответ с тем же ключом повторно отдаёт уже созданную запись. Все сервисы возвращают ошибки в формате `application/problem+json` с полями `type`, `title`, `status`, `detail`, `traceId`.

### Тесты

```bash
npm install
npm test
RUN_INTEGRATION=1 npm run test:integration
```

Интеграционный тест запускается после Compose и проходит путь Gateway → catalog → enrollment → RabbitMQ → payment → RabbitMQ → enrollment. Он также проверяет идемпотентность повторного POST.

## Лабораторная работа 5 CI CD

Конфигурация GitHub Actions находится в [.github/workflows/ci.yml](.github/workflows/ci.yml). Пайплайн запускается на `push` и pull request в `main`, устанавливает зависимости с npm-кэшем, запускает unit-тесты, собирает Docker-образы четырёх сервисов и поднимает Compose для интеграционного теста. При успешном `push` в `main` он публикует все четыре бизнес-сервиса в Docker Hub. Инструкция по созданию Docker Hub token, секретов GitHub и запуску опубликованных образов — в [docs/cicd.md](docs/cicd.md).
